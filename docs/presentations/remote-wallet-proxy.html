01 · propósito

De wallet remota a wallet programable

01Qué cambia
Antes

Una conexión para enviar y recibir

La RemoteWallet exponía capacidades NWC, balance y actividad. La lógica de proxy pertenecía al operador y al LUD-16 global.

  • Destino único en el proxy global
  • Configuración administrativa
  • Sin automatización owner-scoped
→
Ahora

Cualquier usuario crea su propio proxy

La wallet conserva una acción FORWARD versionada: uno o varios destinos, comisión configurable y trazabilidad por recibo.

  • Disponible para NWC activo + SEND_RECEIVE
  • Configurable al crear o después
  • El proxy global sigue independiente
Dos motores, sin mezclar ownershipLa abstracción admite drivers futuros

04 · money model

Cada millisatoshi tiene destino

04Importes
retenido = ceil(bruto × feeBps / 10.000) + base
neto = bruto − retenido

Reglas que evitan deriva

  • Todo se calcula con enteros en millisatoshis.
  • Largest-remainder reparte el neto de forma exacta y determinística.
  • Si el neto ≤ 0, el receipt termina como RETAINED.
  • Antes de facturar se reserva 1% + 1 sat; fee real y sobrante se registran aparte.

06 · state machines

Dos máquinas de estado, una verdad económica

06Estados
Receipt

Estado agregado

RECEIVED→FORWARDING→COMPLETED
PARTIALBLOCKEDRETAINED

PARTIAL significa que al menos un tramo ya fue pagado y nunca se revierte. BLOCKED requiere evidencia o intervención antes de avanzar.

Leg / Attempt

Estado por destino

READY→PENDING→SUCCEEDED
UNKNOWNREJECTEDEXPIREDSUPERSEDED

Solo READY / REJECTED / EXPIRED son adelantables por retry. Un resultado incierto jamás dispara otro pago.

Terminal no significa siempre éxitoLa UI deriva el estado desde evidencia persistida

Workers concurrentes

Dos workers no reclaman el mismo receipt. Otros receipts sí pueden progresar en paralelo.

Ambigüedad segura

Después de timeout, UNKNOWN congela el tramo: primero se demuestra el resultado.

Ownership global

Triggers impiden que una factura destino pertenezca a dos legs o a ambos motores de proxy.

08 · failure handling

Los fallos se convierten en evidencia

08Recovery
Situación Respuesta Garantía
Evento duplicado Conflict-safe insert por walletId + paymentHash. No duplica receipt ni saldo.
Importe ausente Crea registro bloqueado y recupera con lookup_invoice. El ingreso no desaparece.
Invoice hasta 10 sats menor Se acepta; la diferencia queda como shortfallMsats. Nunca paga más de lo reservado.
Timeout después de pagar Attempt pasa a UNKNOWN y espera journal / notification / lookup. No hay double spend por retry ciego.
Éxito parcial Conserva legs exitosos; reintenta únicamente obligaciones no pagadas. Nunca revierte un pago final.
Reconfiguración Exige pausa, cero intentos inciertos y supersede legs no pagados. La nueva revisión respeta lo ya enviado.
Retries automáticos cada 10 minutosRetry manual solo adelanta nextRetryAt seguro

SSE

remote-wallet-forwarding:updated

Se emite en ingresos, attempts, retries, cambios de configuración y estados terminales.

El evento no transporta datos: solo invalida queries owner-scoped. Así ningún cliente recibe información de otro usuario.
